# Changelog

All notable changes to this template set are documented here. Versioning starts at 1.1.0 (2026-07-08); everything before that was tracked by date only, so those older entries are kept as-is rather than renumbered retroactively.

## [1.4.0] - 2026-07-22

Addresses two community-reported issues ([#2](../../issues/2), [#3](../../issues/3)) plus a self-inflicted retention problem noticed while investigating them.

### Fixed
- **Protect NVR-level items (Application Version, Database Corruption State, Hard Drive Compatibility State, Camera License Capacity/Utilization, Storage Utilization/Available/Allocation Mode, Disk Array Total/Used/Available/Capability, Recording Globally Disabled, Offline Camera Count) no longer appear on every console.** These 14 items lived directly and unconditionally on `Ubiquiti UniFi API Host` since [1.3.0], so every discovered console got them regardless of whether it actually runs Protect - on a non-Protect console they'd just sit showing neutral/blank values. Moved them into a new `Discover Protect NVR` LLD rule (item prototypes, `master_item: unifi.protect.bootstrap`) whose preprocessing only yields an entity when `nvr` is non-null, mirroring the existing `Discover Protect Storage Disks` pattern for per-disk items. Consoles without Protect now simply don't have these items at all. Note for existing installs: because item prototypes are a different Zabbix entity type from plain items even when the uuid is unchanged, re-importing this version will drop and recreate these specific items on consoles that *do* run Protect, resetting their history for just these 14 items (everything else - cameras, chimes, per-disk health - is unaffected).
- `Protect Bootstrap Raw`'s final `JSON.parse(res.body)` had no guard against a non-JSON body. Confirmed live: some consoles return HTTP `200` with a non-JSON body from this endpoint when Protect isn't installed, rather than a `404` - the existing `404`/`403`/non-`200` branches all handled cleanly, but this case fell through and threw `SyntaxError: invalid json`, marking the item (and everything depending on it) "not supported" on affected consoles. This predates this session's changes. Now treated the same as `404` - a neutral `{nvr: null, ...}` result instead of a hard failure.
- **Network device discovery (UAP/USW/UPS/RPS/Other) no longer requires local network access to the console.** The four "Discover Host X Devices" LLD rules were gated on `unifi.host.session`'s `master_item`, which only produces a value after successfully logging into the console's *local* controller - so for a cloud gateway with no local Zabbix proxy reachable, per-device discovery never ran at all, even though the device data itself comes from the cloud `/v1/devices` call, and even though every per-device local raw item (`unifi.uap.device`, `unifi.usw.device`, etc.) already independently re-authenticates on its own rather than depending on the inherited token. Added a new cloud-only item, `unifi.api.host.devices` (`Unifi API Raw: Host Devices`, `https://api.ui.com/v1/devices?hostId={$HOSTID}`, 1m), and repointed all five discovery rules' `master_item` to it instead. This means the per-device "Status" item + "`{HOST.NAME}` is offline" trigger already in the `Ubiquiti UniFi Device` template (itself 100% cloud-sourced) now actually gets a chance to run for cloud-only consoles - previously the host it needed never got created. Local-access users are unaffected other than discovery becoming more reliable (no longer breaks on a transient local login hiccup or rate limit). Protect camera/other device discovery is unchanged and still requires local access - Site Manager's v1 API has no Protect device inventory endpoint, so there's no cloud path available for it.
- Removed the now-dead session-token plumbing (`d.token` / `sessionToken`) from the four Network-device discovery rules' preprocessing, since it was only ever populated by the old `unifi.host.session`-based master item and per-device local items don't need a seeded token to function.

### Added
- New `{$UNIFI.LOCAL.API.ENABLED}` macro (default `1`) on `Ubiquiti UniFi API Host`. Set to `0` on a console with no local network path from Zabbix to skip local polling for `Local Raw (Combined)` and `Protect Bootstrap Raw` - both `CALCULATED` items where all HTTP calls happen in our own preprocessing, so the macro is checked before any request is attempted, failing fast and cleanly instead of timing out. This does **not** (and, on this Zabbix item model, cannot) stop `Local Session + Cloud Devices Raw`'s login POST or the per-device local raw items (UAP/USW/UPS/RPS) from attempting their request - those are plain HTTP agent items whose request Zabbix's poller fires before any preprocessing runs, so no template-side macro can gate them. For a genuinely cloud-only console, raise `{$UNIFI.LOCAL.POLL.INTERVAL}` / `{$UNIFI.SESSION.REFRESH.INTERVAL}` / `{$UNIFI.CONSOLE.POLL.INTERVAL}` instead, to make those unavoidable failures rare rather than constant. Cloud-only device offline detection is unaffected either way, since it only ever called `api.ui.com`.

### Changed
- **Shortened raw `history` retention on 53 high-cardinality, high-frequency item prototypes** (per-port items on gateways/switches, per-radio items on APs, per-RPS-port items) that update on every poll of their master item (`{$UNIFI.LOCAL.POLL.INTERVAL}`, default `10s`) with no `DISCARD_UNCHANGED_HEARTBEAT` step to throttle writes - port up/down flap state, STP state, SFP fault flags, rx/tx rates, errors, dropped counts, link-down/MAC-table counts, PoE power, satisfaction/anomaly scores, SFP analog readings, and radio channel/width/tx-power/utilization/retries/client-count. At 90 days retention and a 10s poll interval this is up to ~778k raw rows per item, multiplied by every port on every switch/gateway and every radio on every AP - almost certainly the real driver behind unrelated reports of the Zabbix history tables filling the database. Numeric items (which already had `trends: 365d` enabled) dropped to `history: 14d` - long-term graphing is unaffected since trends already cover that; only the raw drill-down window shrank. The handful of `TEXT`-typed flap/state items (which cannot have trends at all - Zabbix trends only support numeric types) dropped to `history: 7d`, still far more than the `#10`-sample/`24h` lookback the flap-detection triggers actually need. Items already throttled by `DISCARD_UNCHANGED_HEARTBEAT` (port name/duplex/autoneg/uplink/QoS, SFP vendor/part/serial) were left at 90 days since their write volume was already low. This only changes retention, not any collected data or trigger logic - if you want to keep more raw history for a specific host, override the item's history period directly on that host after import (per-host overrides survive re-import). This is a template-side mitigation only; if your history tables are already large, Zabbix's own housekeeping still has to work through the backlog, and it's worth separately checking that housekeeping is actually keeping up (Administration > Housekeeping) and, on MySQL especially, that the history/trends tables are partitioned - unpartitioned `DELETE`-based housekeeping on tables this size is a common real-world cause of housekeeping perpetually falling behind even with sane retention settings.

## [1.3.0] - 2026-07-11

Adds UniFi Protect monitoring (cameras, NVR, and other Protect devices) as two new templates, built entirely on top of the shared session-token architecture from [1.2.0] - no new logins, no new credentials.

### Added
- Two new templates: `Ubiquiti UniFi Protect Camera` (cameras and doorbells) and `Ubiquiti UniFi Protect Device` (chimes today; sensors/lights/sirens/viewers automatically if adopted later), discovered via two new LLD rules (`Discover Host Protect Cameras`, `Discover Host Protect Other`) on `Ubiquiti UniFi API Host`.
- New `unifi.protect.bootstrap` `CALCULATED` item mirrors `unifi.local.all`'s design exactly: reads the cached session token via `last(//unifi.host.session)` and fetches UniFi Protect's local bootstrap endpoint (`/proxy/protect/api/bootstrap`) on its own schedule (`{$UNIFI.CONSOLE.POLL.INTERVAL}`). Confirmed live that the same session cookie already authenticating Network API calls also authenticates Protect, as long as the account has also been separately granted Protect permission in UniFi OS (documented in the README's "Prepare Local Controller Credentials" step) - this is a distinct grant from Network access and not automatic, confirmed live via `/api/users/self`'s `permissions` object showing `network.management` with no `protect.management` key until the role was explicitly re-saved.
- That fetch distinguishes three outcomes: `200` returns the bootstrap payload; `403` throws a clear error naming the missing Protect permission grant (a real misconfiguration worth surfacing loudly, same philosophy as the `{$APIKEY}` propagation fix in [1.2.0]); `404` returns a neutral empty result rather than an error, so consoles that don't run Protect at all (most sites in a mixed fleet) simply discover zero Protect hosts with no noise.
- Camera items/triggers: connectivity (`state`), Protect's own recording-gap detector (`isMissingRecordingDetected` - the sole recording-health trigger, since raw `isRecording` legitimately reads `false` on any camera not set to continuous recording), recordings-paused (+ reason), firmware update available, uptime/recent-reboot, and an informational SSH-enabled flag. `isPoorNetwork` is collected but not alarmed on, matching this template's existing convention for soft quality metrics - UAP/USW satisfaction and channel-utilization items have never had triggers either.
- Camera `Link Speed` (wired PHY rate) alongside the existing connectivity/recording/firmware items - collected as data only, no alarm, consistent with how satisfaction/channel-utilization items are treated elsewhere in this template.
- NVR-level items/triggers added directly to the existing `Ubiquiti UniFi API Host` template - the same console host already monitored for Network, since Protect's NVR state describes the same physical box, not a separate device: database corruption state, hard drive compatibility, camera license capacity/utilization, storage utilization (dual WARN/HIGH threshold), storage allocation mode, global recording-disabled flag, and an NVR-side aggregate offline-camera count as a belt-and-suspenders check alongside the per-camera trigger.
- Whole-array storage view (`Disk Array Total/Used/Available/Capability`, sourced from `systemInfo.storage`) alongside Protect's own recording-space accounting - the two measure slightly different things (raw filesystem vs. Protect's logical accounting) and aren't redundant.
- Per-disk health, discovered via a new `Discover Protect Storage Disks` item-prototype LLD rule (mirroring the existing `Discover Radios` pattern) to support NVR hardware with multiple bays: health state, operational state, bad sector count, temperature, power-on hours, current action (e.g. an active RAID rebuild, with rebuild progress/ETA), state reason, size, and serial number (with an INFO change-detection alarm for a physical drive swap, the same idiom already used for SFP module serial changes). Disk temperature uses new dedicated `{$UNIFI.PROTECT.DISK.TEMP.WARN}`/`{$UNIFI.PROTECT.DISK.TEMP.HIGH}` macros rather than reusing an existing pair, since spinning HDD media runs at different temperatures than gateway/network hardware and every other hardware class in this template already gets its own tier-specific pair.
- `hardDriveState`'s only confirmed value live was a bad one (`hddNotCompatible`, on a real system); rather than guess at a "healthy" string to build an allowlist against and risk a false alarm on day one, it's denylisted specifically plus backed by an INFO `change()` safety-net trigger - the same idiom already used for `unifi.api.host.controller.version` - so any future transition is visible even before it's individually handled.
- New host groups `Type:UnifiProtectDevice` (broad) and `Type:UnifiProtectCamera` (narrow), mirroring the existing `Type:UnifiNetworkDevice`/`Type:UAP` pattern.

### Changed
- `hardDriveState = hddNotCompatible` downgraded from WARNING to INFO after review: it's a compatibility/support notice (the drive isn't on Ubiquiti's certified list), not evidence of an active fault - a drive can run this way indefinitely with no real issues. The per-disk Health/State/Bad Sectors alarms are the actual fault signals; this one is just informational context.
- Protect storage utilization thresholds recalibrated after live testing showed the original 85%/95% pair (borrowed from generic disk-usage conventions) firing constantly at normal steady-state: continuous recording is designed to run near-full and automatically overwrite the oldest footage once full, so mid-to-high-90s utilization is expected behavior, not a warning sign. Dropped the WARNING tier entirely and raised the single remaining HIGH threshold (`{$UNIFI.PROTECT.STORAGE.HIGH}`) from 95% to 99%, so it now only fires when utilization is high enough that the automatic recycling genuinely isn't keeping pace.
- Gateway and switch RX/TX dropped-packet alarms (from [1.1.0.1]) redesigned after live testing showed them flapping every poll cycle on a real link: the original `change()>0` logic fired on *any* counter increase, but a low, steady trickle of drops turns out to be normal background behavior (congestion, buffer limits), not evidence of a problem - the trigger's own description already conceded as much. All four triggers (RX/TX dropped, gateway and switch) now compare growth over a rolling time window against a real count threshold instead: `last() - min(window) > threshold`. New macros `{$UNIFI.PORT.DROPPED.WINDOW}` (default `5m`) and `{$UNIFI.PORT.DROPPED.WARN}` (default `1000`, explicitly flagged as a starting point rather than a value derived from a large sample of real links) control this, declared on both `Ubiquiti UniFi API Host` (gateway ports) and `Ubiquiti UniFi USW` (switch ports). RX/TX Errors triggers use the identical `change()>0` idiom and may have the same flapping risk on a busy link, but weren't reported as currently flapping, so were deliberately left unchanged this round.
- **`{$UNIFI.LOCAL.POLL.INTERVAL}`'s default dropped from `2m` to `10s`** (root template, every console/device tier it propagates through, and both new Protect templates - eight declarations in total). This is the per-device poll interval covering UAP/USW/UPS/RPS and now Protect cameras/other devices; it has had zero login attached to it since [1.2.0]'s shared session-token work (it's a plain GET using the cached token), and real console CPU/memory graphs under this cadence showed comfortable headroom, so there's no longer a reason to hold it back at a conservative `2m`. **`{$UNIFI.SESSION.REFRESH.INTERVAL}` (the actual login, default `10m`) is unchanged** - this only speeds up how often devices are *read*, not how often anything *logs in*. If a device or console host already has its own explicit `{$UNIFI.LOCAL.POLL.INTERVAL}` macro override, that takes priority as always and won't move to `10s` on its own; only hosts actually inheriting the template default pick up the change.

### Considered and not added
- UniFi Protect's own UI displays an "Estimated N Days" retention figure per quality tier (HQ/LQ), but the underlying bootstrap fields (`estimatedHqRetentionDays`/`estimatedLqRetentionDays`) were confirmed `null` on a live, freshly-polled system regardless, and no dedicated storage-stats endpoint was found on that console to fetch the real computed value directly (five plausible endpoint paths tried, all `404`). The UI's figure is almost certainly computed client-side from raw rate/capacity stats using a formula not exposed by any tested endpoint - reverse-engineering it risked showing a confidently wrong number, which is worse than showing none. `Disk Array Available` / `Protect Storage Available` (above) are reliable, always-populated proxies for capacity awareness instead.

### Fixed
- Numeric Protect fields that UniFi can legitimately report as JSON `null` were being rejected by Zabbix with `Value of type "string" is not suitable for value type "Numeric (float)". Value "null"` (first caught live on `estimatedHqRetentionDays`, since removed - see "Considered and not added"). A JSONPath step resolves a JSON `null` to the literal text `"null"` rather than failing outright, so `error_handler: CUSTOM_VALUE` - which only catches an unresolved path - never got a chance to substitute the intended fallback. Every numeric Protect item (roughly a dozen, including several added defensively even where live data hadn't shown a `null` yet) now has an explicit JavaScript step that catches the literal `"null"` string before Zabbix's own type coercion sees it.
- Per-disk `Power-On Hours` used plain `h` units, which Zabbix auto-scales with metric prefixes for large values (e.g. `9369 h` displayed as `9.37 Kh`) - technically correct but an unfamiliar way to read a SMART-standard metric. Changed to `!h`, which tells Zabbix to display the literal hour count without prefix scaling.
- `Discover Host Other Devices` (the generic catch-all for unrecognized device types) was silently claiming every Protect device on a console - confirmed live via the cloud devices API that Protect cameras/doorbells/chimes are all tagged `productLine: "protect"`, and were already appearing as generic `Ubiquiti UniFi Device` hosts before this release. Added a `{#PRODUCTLINE}` exclusion condition (the field was already being discovered by that rule, just not filtered on) so Protect devices are claimed by the new dedicated rules above instead, preventing a duplicate host per Protect device on upgrade.

## [1.2.0] - 2026-07-08

Eliminates the redundant per-device local controller logins documented as a known limitation in [1.1.0]: every device on a console now shares one cached session token instead of logging in itself every poll.

### Changed
- `unifi.host.session` (`Local Session + Cloud Devices Raw` - see "Renamed" below) now logs into the console's local controller itself (every 10m by default, alongside its existing cloud fetch) and attaches the resulting session token to its output. The four "Discover Host X Devices" LLD rules (UAP/USW/UPS/RPS) propagate that token to every discovered device via a new `{$UNIFI.SESSION.TOKEN}` host macro, the same mechanism already used to propagate `{$UNIFI.LOCAL.IP}`/`{$UNIFI.USERNAME}`/`{$UNIFI.PASSWORD}` from console to device.
- The four per-device raw items (`unifi.uap.device`, `unifi.usw.device`, `unifi.ups.device`, `unifi.rps.device`) no longer log in at all - they GET the local controller directly using the cached token. Local controller logins per console drop from `1 + N` (one per device, every cycle) to a flat `2`, regardless of device count. Confirmed live that a single cached token can be reused for repeated GETs with zero rate-limiting; the rate limit is specific to concurrent *login* volume, not general request volume.
- If a device's cached token is ever rejected (console reboot, a missed propagation cycle), its own item now detects this from the response shape and performs a one-off fresh login right then, self-healing within the same poll cycle instead of waiting on the console's next scheduled refresh. This only costs a login in that rare case - normal operation stays at zero device-level logins.
- Per-device poll interval is now configurable via a new `{$UNIFI.LOCAL.POLL.INTERVAL}` macro (default `2m`, down from a hardcoded `3m`). It flows through the same three-tier chain as `{$UNIFI.USERNAME}`/`{$UNIFI.PASSWORD}`: a real default lives once on the root `Ubiquiti UniFi API` template, `Discover Unifi Hosts` propagates it to every console, and the four "Discover Host X Devices" rules propagate it again from console to device - so changing it once at the root changes it everywhere, while a console or an individual device can still override it locally. The old interval existed specifically to limit login frequency, which no longer applies now that the per-device item doesn't log in.
- `Local Raw (Combined)` (`unifi.local.all`) and `Local Session + Cloud Devices Raw` (`unifi.host.session`) no longer both log in independently. `unifi.host.session` keeps doing its own login, on its own new `{$UNIFI.SESSION.REFRESH.INTERVAL}` schedule (default `10m`, raised from its previous hardcoded `1m` - see reasoning below). `unifi.local.all` is now a `CALCULATED` item instead of an `HTTP_AGENT` one: its formula (`last(//unifi.host.session)`) reads whichever session token `unifi.host.session` most recently minted, without triggering a new poll of it. This lets `unifi.local.all` run on its own fast, independent schedule (`{$UNIFI.CONSOLE.POLL.INTERVAL}`, default `3m`, unchanged, but safe to set much lower - e.g. `10s` - if you want fast WAN/health telemetry) without that speed also being how often it logs in. If the cached token is ever missing or rejected, `unifi.local.all` performs one fresh login itself for that poll only - the same fallback pattern used by the per-device items. This is the only native Zabbix mechanism that can decouple a fast poll from a slow login refresh on the same host: a `DEPENDENT` item would tie `unifi.local.all` to `unifi.host.session`'s exact (slow) schedule, and there is no way for an item to write a macro back onto its own host, so `CALCULATED` + `last()` is what makes this work.
- `{$UNIFI.SESSION.REFRESH.INTERVAL}`'s default was deliberately raised to `10m` rather than kept at a faster value: the session-mint login itself is cheap (O(1) per console regardless of device count), but UniFi's local rate limiting is only confirmed to trigger on concurrent logins - a sustained rate of frequent logins hasn't been tested, so `10m` keeps total login attempts low regardless, while still maintaining a comfortable margin against the ~2 hour session token lifetime.

### Fixed
- All three new interval macros (`{$UNIFI.LOCAL.POLL.INTERVAL}`, `{$UNIFI.CONSOLE.POLL.INTERVAL}`, `{$UNIFI.SESSION.REFRESH.INTERVAL}`) now carry a real fallback value at every template tier they pass through (root, console, and - for the per-device one - the UAP/USW/UPS/RPS templates too), not just at the root. Without this, a host that hadn't yet been through a full discovery cycle after import could end up with the macro resolving to an empty string, which Zabbix rejects outright as `Invalid update interval ""` rather than failing gracefully - unlike `{$UNIFI.USERNAME}`/`{$UNIFI.PASSWORD}`, where an empty value just fails a login cleanly, an empty `delay` is a hard configuration error. The propagated value still takes precedence once discovery has run; the template value is only a safety net for the gap before that.
- `{$APIKEY}` is now propagated from the root host to every discovered console, the same way `{$UNIFI.USERNAME}`/`{$UNIFI.PASSWORD}` already are. Previously it was only ever a root-host macro with no propagation path to consoles, so any console-level item needing the cloud API (like `Local Session + Cloud Devices Raw`'s cloud fetch) depended entirely on the user separately setting `{$APIKEY}` as a Zabbix global macro or on every console by hand - undocumented and easy to miss on a freshly discovered console, surfacing as a cloud `401`.
- All 15 "raw" items (every item tagged `component: raw`) had `history: 0` ("do not store"), which turned out to mean genuinely zero retention, not just "hidden from Latest data" - the intent was to skip storing large raw JSON blobs long-term since their meaningful fields are already surfaced via dependent items, but this meant a `CALCULATED` item's `last()` function could never retrieve anything from them, no matter how many times they successfully executed. Now set to `history: 1h`: enough for `last(//unifi.host.session)` (see above) to always have something to read, and enough to let a raw item's actual last-fetched value be inspected directly in Latest data when debugging, without materially growing the database.

### Renamed
- The item formerly known as `unifi.api.host.devices` / `Unifi API Raw: Devices` is now `unifi.host.session` / `Local Session + Cloud Devices Raw` - both the key and the display name changed, reflecting that it now does the local controller login too, not just the cloud fetch its old name implied. Renaming the key means Zabbix will remove the old-keyed item and create the new one on next import for every host already using it; with `history: 1h` (see above) there's nothing meaningful to lose.

## [1.1.0.1] - 2026-07-08

A large expansion of per-port monitoring: SFP module metadata, full gateway SFP support (previously switch-only), port renaming/QoS visibility, and several new Ethernet-level fields - plus a template-wide `DISCARD_UNCHANGED_HEARTBEAT` consistency pass.

### Added
- SFP module metadata items: `Compliance`, `Part Number`, `Serial Number`, `Vendor`, `Revision` on switches; `Part Number`, `Serial Number`, `Vendor`, `EEPROM Readable` on gateways (gateways don't expose compliance/revision). An INFO alarm fires when a module's serial number changes, indicating a physical swap rather than a reseat.
- Gateway SFP monitoring, previously switch-only: `Discover Gateway SFP Ports` (TX fault, RX loss-of-signal - the gateway-side equivalent of a switch's RX fault) and `Discover Gateway SFP Optical Ports` (temperature, RX/TX power, voltage, current). Gateways use different field names than switches (`sfp_tx_fault`/`sfp_rx_los` vs. `sfp_txfault`/`sfp_rxfault`) and don't expose an `sfp_compliance` field, so the optical/DAC split uses a part-number-prefix filter instead of the compliance field switches use.
- `Port Name` item for every port (switch and gateway, not just SFP ones), with an INFO alarm when it changes - UniFi auto-renames a port after the connected device's hostname, so this tracks patching changes over time. Previously the port name only existed as a discovery-time label with no history.
- New per-port Ethernet items, switch and gateway, informational unless noted: `Full Duplex`, `Autoneg`, `Is Uplink`, `Link Down Count` (cumulative flap counter), `MAC Table Count` (learned MAC addresses - spot an unexpected hub/switch downstream), `RX/TX Dropped` packets (**new WARNING alarm** if actively increasing, mirroring the existing TX/RX Errors pattern), `STP State` (**new WARNING alarm** if stuck on `blocking`, an active loop-prevention signal), `STP Edge Port`, and `QoS Mode` (surfaces Pro AV/traffic-control profiles like `aes67_audio`).

### Fixed
- Optical-only SFP items (`Temperature`, `RX/TX Power`, `Voltage`, `Current`) were previously created for every SFP-found port, including DAC (direct-attach copper) cables, which structurally can't report any of those values (no laser or photodiode). Confirmed live by comparing the same physical DAC cable from both ends (a gateway-to-switch uplink): identical missing fields on both sides. These items are now only discovered on non-DAC (fibre) modules; DAC ports still get the fault/info tier (TX fault, part number, serial, vendor, etc.), just not the optical measurements that can never populate.
- Extended `DISCARD_UNCHANGED_HEARTBEAT` to 9 more slow-changing metadata items that were missing it inconsistently with their siblings (e.g. `UniFiOS Version` didn't have it while the equivalent per-device `Firmware Version` did): Hardware Type, Public IP Address, Hardware Serial Number, Unifi Stack status, UniFiOS Version, WAN IPv4 Address, WAN Speed Type, per-controller Version, and Radio Band. Items that directly drive an alarm as their primary state input (connection state, blocked, WAN enabled, outlet relay, RPS state, etc.) were deliberately left alone, so they keep a live timestamp at all times.

## [1.1.0] - 2026-07-08

Mostly about false-positive alerts caused by transient local/cloud API failures, the UniFi API returning consoles outside a key's configured scope, and an easier way to set shared local credentials. No template architecture changes.

### Added
- Per-port `Anomalies` item for switch ports and gateway ports (`unifi.usw.port.anomalies[{#PORTID}]` / `unifi.gw.port.anomalies[{#PORTID}]`), alongside the existing per-port `Satisfaction` item. Both are plain monitored values with no trigger attached.

### Fixed
- UniFi's Site Manager API does not enforce an API key's configured site restrictions on `/v1/hosts` or `/v1/sites` - both endpoints always return every console on the account regardless of the key's configured scope (confirmed via direct testing with a site-restricted key). Added `{$UNIFI.SITE.EXCLUDE}`, a client-side workaround macro that filters excluded consoles (matched by hostname, full host ID, or host ID prefix) out of discovery before they're turned into Zabbix hosts. ([#1](../../issues/1))
- Local controller raw items (gateway, UAP, USW, UPS, RPS) no longer treat a failed login/request (timeouts, `429` rate limiting, etc.) as "device not found." Previously, any request failure was silently converted into an empty/fake successful response, which downstream items read as the device being offline, causing false "offline - not seen by local controller" and false `0`-value readings during ordinary network blips or controller rate limiting. A failed poll is now simply skipped (last known value is kept) rather than misreported.
- Confirmed via live testing against a real console: 10 concurrent local controller logins returned `429` on 7 of them, explaining why consoles with many devices (each device independently logging in every poll cycle) were seeing periodic false-offline flapping lasting close to the old 5-poll persistence window.
- Fixed the trigger-prototype dependency on the offline triggers, which requires matching the target's `recovery_expression` exactly, not just name and expression, or Zabbix reports the dependency as "does not exist" on import.
- Per-port `Satisfaction` items (switch and gateway) had no `value_type` set, defaulting to Numeric (unsigned), which can't store the `-1` fallback used when a port doesn't expose this field. Every device-level `Satisfaction` item already correctly used `FLOAT`; the port-level ones just missed it. Confirmed live that some switch models (e.g. `US24PRO`) never expose per-port satisfaction at all, regardless of link state, so this fallback path is hit routinely, not just on edge cases.

### Changed
- **"{HOST.NAME} offline - not seen by local controller"** triggers (UAP/USW/UPS/RPS) now alarm on the first genuinely bad poll and recover on the first good poll, instead of requiring 5 consecutive bad/good polls in each direction. This is safe now that transient failures no longer produce fake bad readings (see Fixed, above): a bad reading only ever comes from the controller genuinely reporting the device down.
- Local controller credentials (`{$UNIFI.USERNAME}` / `{$UNIFI.PASSWORD}`) can now be set **once** on the root host and are automatically inherited by every discovered console, instead of requiring manual entry on every console individually. A per-console override still works for sites needing different credentials.

### Removed
- Two unused root-level cloud API items (`Unifi API Raw: Devices` - `GET /v1/devices`, and `Unifi API Raw: Sites` - `GET /v1/sites`) that were polled every minute with zero downstream consumers anywhere in the template.

### Investigated, no change made
- Tried to fix the redundant polling at its source: have each device read the console's already-fetched local/cloud data instead of re-fetching it itself. Not possible with Zabbix's built-in item types. `DEPENDENT` items require the master item on the same host, and `CALCULATED` items need a literal host name baked into the formula at save time, before any macro is resolved, but console and device host names only exist once LLD has discovered them. Reverted the attempt. The only way to genuinely fix this is turning per-device metrics into LLD item prototypes living on the console host instead of giving each device its own Zabbix host, which is a real architecture change, not a drop-in fix. Documented as a known limitation in the README instead.
- Also considered just merging each device's local and cloud raw items into a single item, purely to cut the item count. Rejected: it doesn't reduce the number of actual HTTP requests at all (still one login, one local fetch, one cloud fetch, regardless of how many Zabbix items they're wrapped in), and it would couple two failure modes that are usefully independent today.
